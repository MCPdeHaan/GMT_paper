# Step 16: replication audit and architecture

The frozen scope is all files ending in .rds or .csv under data/processed, including all diagnostics. It contains 128 RDS files and 232 CSVs (232,607,404 bytes), with 9,072 ordered column records, of which 6,758 are numeric. The RDS manifest exposes separate `files` and `columns` tables. The CSV is their flattened representation. Two named-list RDS files have member schemas and member counts instead of an invented file-level row count. Numeric summaries use finite values and record nonmissing, NA, NaN and signed-infinity counts. CSV types were inferred over the full file. An all-empty or mixed-type CSV column may therefore have a different inferred type from the original R object. The authoritative exact check is SHA-256 of the original file bytes.

Run `Rscript --vanilla tests/verify_golden_step15.R` with R 4.6 or later. The verifier checks path coverage and every file hash, with a non-zero status for any missing, added or changed file. A temporary negative test exercised all three failure modes. The existing 346 assertions pass. This phase added only audit files under tests.

[Code inventory](step16_code_inventory.csv) lists every root code file, its line count, role, inputs and outputs. [Output registry](step16_output_registry.csv) assigns every frozen path to a target owner or explicit retirement. The reader column is an index of identifiable literal references, supplemented for dynamic ledger names. It is not a complete function-call graph or a licence to remove an output with a blank reader. Output classification used parsed R expressions, manually resolved dynamic names, source chains, test and exhibit references, and focused reads of the identified producers and consumers. No exhaustive proof of runtime reachability or fresh checkout run was performed.

## Directory decisions

- `data/processed_backup_2017_2022/` has 126 RDS and 173 CSV files, all byte-identical to the corresponding files in `data/baseline_processed/` and `data/baseline_diagnostics/`. Retain one canonical thesis archive or a hashed projection of the inputs required by comparison, and retire the duplicate only after the ILO fallback, tests and scorecard are migrated.
- `writing/baseline_generated/` has 64 TeX files and no active reader found. Of 59 paths shared with current generated output, only three are byte-identical. Archive as a thesis release.
- `writing/final document/` contains the thesis PDF, a ZIP and 18 duplicate source filenames. Nine source copies match the current files. The ZIP has no substantive data payload. Keep it as the submitted thesis archive and exclude it from the journal deposit.
- `writing/intermediate documents/` holds 26 drafts and `writing/presentations/` is dissemination material. `writing/publication_plan/` and the root handbook contain planning material. Archive separately from the replicator-facing tree. Keep bibliography, source and figures needed by the actual manuscript.
- `literature/` holds 236 files, about 194 MB before filesystem block accounting, including third-party TWZ spreadsheets, data, scripts and papers. No active pipeline reference found. Publish source citations and necessary authorised inputs only. Assess rights for every retained dataset, even if it is publicly downloadable.
- `tmp/` contains only Finder metadata. The tree has 11 Finder metadata files, a tracked empty `.Rhistory`, an RStudio project and editor settings. Exclude session and editor files from the deposit. Keep `data/manual/profit_correction_anchors.csv` as a substantive, documented input.
- `data/raw/` contains 53 non-Finder files, 49 tracked. Archive exact inputs, distinguish vendor downloads from manual extracts and derived raw composites, and remove unused downloads only after the exhibit dependency map is complete.

## Steps 17–19 acceptance

1. **Step 17, deterministic reproduction.** Freeze a baseline revision and exact raw input hashes in addition to the output manifest. Add a root runner, dependency lock and output-root injection. Reproduce the 359 outputs with active writers in a clean directory. The orphan PwC file can be copied from the archival fixture when explicitly exercising the 360-file strict profile. Any mismatch needs a diagnosis and recorded disposition.
2. **Step 18, module migration.** Move functions and side effects into the declared owners. Compare sorted observations by explicit unique key, full column values and types, NA versus zero, and applicable totals. Use exact comparisons for unchanged paths under the pinned environment. For deliberate schema changes maintain the old compatibility export and compare the new keyed projection with a reviewed mapping. Numeric aggregates alone cannot detect offsetting errors or changes in row alignment. Legal and measurement changes get separate commits with before/after tables.
3. **Step 19, paper release.** Prune only against the signed exhibit/dependency map, archive the thesis and historical fixtures once, and run on a fresh machine from the deposited files. Include raw-input provenance and rights, codebooks, exact installation commands, R/Python/package and LibreOffice versions, runtime and memory, seed/locale/thread settings, a data availability statement and a mapping from each exhibit to the command and inputs that regenerate it. Keep a root README in Markdown and PDF. Deposit in a trusted repository with a persistent identifier and test the deposited archive itself.
